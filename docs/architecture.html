Veranico.

A parametric rainfall cover agent for Brazilian agriculture. A broker describes a farm's weather exposure in plain language; the agent loads decades of ERA5-Land reanalysis, backtests a trigger, prices the cover, drafts a term sheet and requests a submission that only a person can approve.

ShapeModular monolith in Python, seven business modules
Deployable rolesOne image: APP_ROLE=api and APP_ROLE=carrier
StateFirestore in Native mode; Cloud Storage for blobs
Async deliveryTransactional outbox, Cloud Tasks, Cloud Scheduler sweep
AgentHand-written loop on the Anthropic Messages API
HostingCloud Run in us-central1, scale to zero

1What it is.

One conversation takes a broker from a described exposure to a backtested trigger, an indicative price, a bilingual term sheet and a submission waiting for a human decision. The system exists to carry two proofs.

Proof 1
Basis risk on the map

A farm can sit in a grid cell that rarely triggers while a cell a few kilometres away triggers often. pricing computes a metric for every cell of a regional weather cube (trigger_frequency, season_anomaly) and the map draws it over real terrain, with the insured cell outlined against its neighbours.

Proof 2
No ungrounded figure, human approval

The agent never states a number that did not come from a deterministic tool, and every price carries a quote_id. A pure function checks each answer against the tool results at run time. Only a browser session that owns the workspace can approve a submission: no agent tool and no API key can.

Consequence
Two consumers, one service

The agent, through its tools, and brokers integrating directly, through the public API, call the same module facades. The agent never has a capability the public API lacks, and the reverse.

Scope of this document. It describes the architecture fixed in SPEC.md (scope locked on 2026-11-10) and the frozen module contracts. The specification stays the source of truth; a contract changes only through a decision record under specs/adrs/. Measured results belong to verification.md, not here. Pricing is illustrative and is not actuarial or insurance advice; the demo is non-commercial.

4Data ownership.

Each module owns its Firestore collections (prefix <module>_) and its Cloud Storage prefix (<module>/). No module reads another module's data.

ModuleFirestore collectionsCloud Storage prefix

assistantassistant_conversations (subcollection messages)none
  • Workspace-scoped documents carry expires_at for the Firestore TTL policy (default 14 days), so an anonymous workspace and everything in it expires on its own.
  • There are no foreign keys. Invariants live in code and transactions, and another module's data is referenced by identifier (QuoteId, DatasetId, WorkspaceId) and read through its facade.
  • The audit trail is an append-only subcollection of the quote.
  • pricing persists nothing: its results are deterministic and the per-cell metrics are cached in process per region, index definition and season.
  • An architecture test checks that a module touches only the collections and prefixes it owns.

5Three flows.

The chat turn carries the grounding proof, the approval path carries the human gate and the delivery guarantees, and the weather paths explain where every series comes from.

5.1 A chat turn

POST /chat returns a server-sent event stream. The loop is written by hand on the Messages API so that every limit and failure path is visible in code.

ToolModule behind itOutputSide effects
resolve_locationclimateLocation, or LocationCandidates when the name is ambiguousnone
get_weather_historyclimateDatasetRefmay ingest and cache
backtest_indexpricingBacktestResultnone
price_coverquoting, which prices through pricingquote_id and PricedCoverpersists a draft quote
find_extreme_seasonspricinglist[ExtremeSeason]none
draft_term_sheetdocumentslist[DocumentRef], one per languagerenders and stores the PDFs
request_submissionquotingSubmission, status pending_approvalcreates a pending approval, idempotent per quote
  • Tools are thin adapters. Every input and output is a Pydantic model. A validation error becomes an invalid_arguments tool error with the field and the reason; no exception reaches the model.
  • Bounded retries. The model may retry a failed tool once with corrected arguments. After two consecutive failures of the same tool it stops and explains. On reaching the limit of 10 tool calls in a turn, the agent stops and says what is done and what is pending.
  • Model failure mid-turn. The stream ends with an error event that lists the tools that completed. The conversation stays usable.
  • Durable memory. Every message and every full tool result is stored in Firestore under the workspace, so any instance can continue a conversation. Compaction is deterministic and done by code: when the prompt estimate crosses a threshold, the oldest tool results are replaced in the prompt by a structured summary built from the stored result. The stored results are untouched. There is no retrieval over documents.
  • One grounding function. check_grounding lives in assistant/domain and is also the numbers_grounded scorer of the evaluation suite.
  • Replay. When the live agent is unavailable to a visitor, GET /replays/{locale} plays a recorded conversation, labelled as a recording. A replay creates no quote and no approval.

5.2 Approval to receipt

The agent can only request a submission. A person decides, and from that decision to the carrier's receipt no step can be lost by a crash or duplicated by a retry.

draft→ pending_approval→ approvedorrejected · approved→submitted when the receipt is recorded
  • Who can decide. Only POST /api/v1/approvals/{id}/decision, called from a browser session that owns the quote's workspace, moves a quote out of pending_approval. decide raises forbidden for any other principal and invalid_state for any other state. Two concurrent decisions on one approval produce exactly one outcome.
  • Why an outbox. The decision, the audit entry and the SubmissionApproved event commit together, so an approved quote always has an event to deliver, and a failed transaction leaves nothing behind.
  • Why a sweep. A crash between the commit and the enqueue leaves an event nobody scheduled. The sweep, called by Cloud Scheduler and opportunistically when the approvals queue is read, finds and enqueues it.
  • Safe to repeat. The task is named after the event id, record_delivery_attempt is idempotent per event id and attempt, and the carrier deduplicates by event id: a replayed event returns the original receipt.
  • Signature. Veranico-Timestamp carries Unix seconds and Veranico-Signature: v1=<hex> carries the HMAC SHA-256 of "<timestamp>.<raw body>" under the shared secret. The carrier answers 401 for a bad signature and 400 for a timestamp older than 300 seconds.
  • What is retried. A 5xx, a timeout or a connection error is retryable; a 4xx is not. After the retry limit the quote stays approved with a delivery-failed marker and the Approvals panel offers POST /approvals/{id}/redeliver.
  • Local and tests. An in-process relay polls the outbox and performs the same delivery call, so the path is restart-safe without Cloud Tasks.
  • Audit. Every transition and every webhook attempt is an audit entry with a timestamp and an actor: agent, human, system or carrier.

5.3 Weather data paths

Both sources deliver the same reanalysis product, ERA5-Land daily precipitation, from 1950 through the last complete year, so results are consistent wherever a point is priced.

  • Validate before writing, on both paths: no duplicate dates, no gaps, no negative precipitation. Anything else fails loudly.
  • Atomic writes: a temporary location and a rename locally; a generation precondition on Cloud Storage.
  • Consistency check: for one point inside each region, a test compares the cube series with the Open-Meteo series over the overlap and asserts that the difference stays within a documented tolerance.
  • Evidence: the exact daily slice used by a quote is exported as NetCDF with provenance attributes (dataset id, grid point, source, request, cube manifest checksum, index definition).
  • Location resolution: free text goes through a geocoding port (default adapter: the Open-Meteo Geocoding API), restricted to Brazil. An ambiguous name returns candidates instead of a guess.
  • Attribution: Copernicus Climate Change Service (ERA5-Land) and Open-Meteo, CC BY 4.0, shown next to the map, in the term sheet and in the README.
Human gate H1, closed on 2026-11-11. The three real cubes were built from Google Earth Engine with a Cloud project registered for it (ADR 0019; the Copernicus CDS account of the first plan could not be created), and the chunking was measured on them (ADR 0016). The pipeline is tested against a small synthetic NetCDF file. The real cubes are not in the repository: a fresh clone, the tests and the evaluation suite serve seeded cubes clearly labelled synthetic in the interface, and the deployed service gets the real ones in Cloud Storage as part of the first deploy.

6Deployment.

One container image, two Cloud Run services, everything in us-central1 and defined in Terraform. Both services scale to zero.

Identities
  • GitHub Actions reaches Google Cloud through Workload Identity Federation. No JSON key exists.
  • Each role runs under its own least-privilege service account.
  • The internal routes (/internal/outbox/…) accept a service identity only; Cloud Tasks and Cloud Scheduler call them.
  • People have no accounts: a browser holds a signed, HttpOnly workspace cookie, and an API client holds a key of that workspace.
Secrets
  • Secret Manager holds the Anthropic key, the webhook signing secret, the cookie signing secret, the allowance code and the IP hash salt.
  • The webhook secret is shared by the two roles: one signs, the other verifies.
  • Earth Engine credentials and project are used only by the offline cube build and never reach the running service.
  • No secret appears in code, fixtures, logs, spans or commits; gitleaks scans the full history.
Life cycle
  • Instances: minimum 0 and maximum 2 per service. Conversations are durable in Firestore, so any instance can continue one.
  • Graceful shutdown: readiness turns false on SIGTERM and open streams end with a final event.
  • deploy.yml runs on tags matching v*.*.*: build, push, terraform apply with the new image tag.
  • Artifact Registry keeps the last 3 images.

7Cross-cutting rules.

Rules that hold in every module: money, errors, text for people, observability, and the limits on access and cost.

Money
Integer centavos, rounded once
  • The numerical engine works in float64 inside pricing/domain.
  • Every monetary value leaves pricing as Money: an integer number of BRL centavos, rounded once, half to even, at the module boundary.
  • Rates and probabilities leave as Rate: fixed-decimal strings with six places. Millimetres and days leave rounded to one decimal place.
  • No module outside pricing/domain does arithmetic on money, and no float reaches JSON as money.
  • The interface renders figures as the API returns them. Formatting for locale is not recomputation.
Errors
Stable codes, not prose
  • Modules raise DomainError subclasses with a stable snake_case code, an HTTP status and a retryable flag.
  • HTTP answers are RFC 9457 problem documents: type, title, status, code, detail, trace_id.
  • allowance_exhausted and spend_ceiling_reached also carry replay_available.
  • Tools return ToolError {error_code, message, retryable} as the tool result, never an exception to the model.
  • The interface translates codes, never English prose.
Internationalisation
A code plus parameters
  • Text for people (assumptions, audit actions, tool summaries, warnings) crosses boundaries as Coded {code, params}.
  • Only presentation layers hold translated prose, in English and Brazilian Portuguese: the HTTP problem mapper, the term sheet and the frontend.
  • The agent answers in the language the user writes in; amounts are in BRL.
  • API field names, codes and logs are English only.

Observability

OpenTelemetry instruments requests, agent turns, model calls, tool calls, webhook delivery and ingestion. Jaeger receives the traces in development and Cloud Trace in production.

http.request └─ agent.turn ├─ llm.call model, input and output tokens, stop reason, latency, cost └─ tool.<name> status, duration, error code outbox.deliver one webhook delivery attempt climate.ingest point history fetched from Open-Meteo
  • The cost of each model call is computed from token counts with prices read from configuration.
  • Structured JSON logs carry trace_id; the same identifier is returned in every problem document.
  • No secrets, raw IP addresses, message text or tool payloads appear in logs or span attributes.
  • Operations are limited to what is free: an uptime check on /health and a billing budget with email alerts.

8How the boundaries are enforced and verified.

The rules in this document are checks that run, not conventions. A change that breaks one fails make lint or a test before review.

The gates

Each milestone ends with one Make target that exits non-zero on failure. A gate includes the fast checks of every earlier gate (lint, types, architecture, unit tests), and a milestone does not start while the previous gate fails. No test, lint rule, type check or threshold is weakened to pass one.

GateWhat it proves about the architecture
make verify-m0Boundaries and types pass on the frozen contracts as code; fakes satisfy the facades; the OpenAPI document and the typed client exist without drift; both roles answer /healthz; the emulators work.
make verify-m1access, the point path of climate and pricing pass their unit and integration tests; the mutation proof kills every mutant.
make verify-m2The NetCDF to Zarr pipeline passes on the synthetic file; per-cell metrics equal a hand-computed grid and return in under one second on a full-size fixture cube; the cube and point sources agree.
make verify-m3The happy path runs through HTTP with a scripted model client, on the emulators, with both roles running; the failure campaign passes; workspace isolation holds; the agent evaluation suite reaches 90% over 3 epochs.
make verify-m4The full flow runs in the browser, including approval and the season view; the embed route sends its frame-ancestors header.
make verify-m5The span tree of section 7 is asserted with an in-memory exporter; the image builds and both roles start; Terraform validates and its tests pass; the load run is followed by the Firestore oracle.
make verify-m6Every requirement has at least one passing test; verification.md is regenerated for the current tree; this document matches the module table; a clean copy of the tree passes make verify-m0.

Evidence is reported honestly: a step counts as passed only when its command ran on the current tree and exited zero, every measured result names its commit, and a gate that needs a missing account is reported as open.
